# Plan 11-02 — MCP Inventory, Refresh, Recovery + Diagnostics

## Objective

Make the actual MCP runtime observable and recoverable: real tool inventory, explicit refresh, owner-local runtime status and actionable failure stages without stale healthy state or unsafe tool-call replay.

## User-visible outcome

An Agent/user can ask ADM what tools an enabled MCP actually exposes, when that inventory was refreshed, whether the runtime is healthy, and why connection/discovery/call failed. A repaired MCP can recover on a later safe refresh/list request.

## Tasks

### 1. Define one owner-local MCP runtime observation model

Record per `(environment_id, mcp_id)`:

- desired enable/config identity references;
- observed state;
- transport;
- failure stage: activation/connect/discover/list_tools/call;
- structured `error_kind` and sanitized message;
- `last_checked_at` / `last_success_at`;
- bounded public tool inventory + `inventory_fetched_at`.

Never persist session/process/health/tool-inventory observations to desired ADM state.

### 2. Add explicit inspect + refresh semantics

Agent-facing operations:

- `environment_mcp_inspect` — desired + current owner observation, sanitized;
- `environment_mcp_refresh` — explicitly drop stale observation/session, activate again and fetch real inventory;
- existing `environment_mcp_tools` remains a real consumption surface and may populate/refresh inventory when needed.

Environment disable/remove must immediately close runtime state and invalidate inventory.

### 3. Make recovery safe

- safe inspection/list/refresh may establish a fresh runtime after a previous transport failure;
- any connection/list error clears stale healthy state;
- tool-call transport/protocol failure invalidates the session;
- **never automatically replay the same tool call** after failure;
- a later caller may explicitly invoke the tool again after inspecting/recovering runtime.

Add an invocation-count helper MCP so hidden replay is caught by tests.

### 4. Improve structured diagnostics

Use stable error kinds and stages for at least:

- disabled/not enabled;
- unresolved definition;
- invalid/incomplete configuration;
- missing secret reference;
- unsupported transport/auth;
- executable not allowlisted / stdio launch failure;
- timeout;
- connection refused/failed;
- auth failure;
- protocol/discovery failure;
- tool-list failure;
- tool-call failure;
- owner closed.

Messages must be useful without embedding secret values or raw sensitive headers/env.

### 5. Restart/reconciliation proof

Through a real Gateway process:

- start with enabled HTTP and/or stdio MCP;
- observe real tool inventory;
- stop Gateway and prove owned child/session cleanup;
- restart and prove desired config survives but old inventory/health does not masquerade as current;
- refresh/list rebuilds current observation.

### 6. Full Phase 11 evidence

Run the Phase 11 validation matrix, race owner refresh/drop paths, regression MCP/Skill/files/verifier/process/generic Run, vet and diff-check. Record any long aggregate tool-timeout separately from product failures.

## Done when

An MCP is no longer just a catalog record plus `ListTools`: ADM has a coherent supported transport model, secure activation, real owner lifecycle, actual refreshable inventory and structured recovery diagnostics, while one broken MCP remains operation-local.
